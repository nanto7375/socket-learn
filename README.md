# TCP 소켓 학습 실습

이 저장소는 Node.js의 `node:net`으로 TCP가 **메시지 목록이 아닌 순서가 보장되는 바이트 스트림**임을 직접 확인하는 여섯 실습을 담고 있습니다. 아래 순서대로 진행하면 설치부터 종료 방식 비교까지 한 흐름으로 학습할 수 있습니다.

## 1. 준비: Node.js 24 이상과 설치

Node.js 24 이상이 필요합니다. 저장소 루트에서 의존성을 설치합니다.

```bash
node --version
npm install
```

## 2. 두 터미널에서 실행하기

각 실습은 저장소 루트에서 실행합니다. 먼저 터미널 1에서 서버(실습 05는 소비자)를 시작하고, listen 로그가 보이면 터미널 2에서 대응하는 클라이언트(실습 05는 생산자)를 실행합니다.

```bash
# 터미널 1
npm run lesson:01:server
```

```bash
# 터미널 2
npm run lesson:01:client -- "안녕 TCP"
```

서버는 `Ctrl+C`로 종료합니다. 기본 포트는 실습 번호에 따라 `4001`부터 `4006`까지입니다. 포트가 사용 중이면 두 터미널 모두 같은 `PORT`를 지정합니다.

```bash
PORT=4101 npm run lesson:01:server
PORT=4101 npm run lesson:01:client -- "다른 포트"
```

## 3. 실습 01: 받은 바이트 그대로 보기

### 실행

```bash
# 터미널 1
npm run lesson:01:server

# 터미널 2
npm run lesson:01:client -- "안녕 TCP"
```

### 예상 관찰

서버의 `data` 로그에는 한 chunk의 `bytes`, `hex`, UTF-8 `text`가 함께 표시됩니다. 한글 한 글자가 화면의 글자 수와 다른 바이트 수를 차지하며, 같은 바이트를 hex와 UTF-8 문자열로 다르게 표현할 수 있음을 확인합니다. 실제 chunk의 개수와 크기, 이벤트 시점은 실행마다 달라질 수 있습니다.

### 생각해 볼 질문

문자열의 글자 수와 `Buffer.length`가 다른 이유는 무엇일까요? chunk 중간에서 UTF-8 다중 바이트 문자가 나뉘면 chunk별 `toString("utf8")` 결과를 그대로 이어도 항상 원문이 될까요?

## 4. 실습 02: `write()`와 `data` 사이에 메시지 경계가 없는 이유

### 실행

서버를 유지한 채 두 모드를 차례로 실행합니다.

```bash
# 터미널 1
npm run lesson:02:server

# 터미널 2
npm run lesson:02:client -- --mode=split
npm run lesson:02:client -- --mode=combined
```

### 예상 관찰

`split`은 두 번에 나누어 쓰고, `combined`는 두 문자열을 묶어 쓰지만 서버의 `data` 이벤트 횟수가 호출한 `write()` 횟수와 반드시 같지는 않습니다. TCP는 애플리케이션 메시지 경계를 전달하지 않으므로, 한 번의 write가 여러 chunk로 나뉘거나 여러 write가 한 chunk로 합쳐질 수 있습니다. 이 실행에서 보인 chunk의 개수·크기·도착 시점은 관찰값일 뿐 계약이 아닙니다.

### 생각해 볼 질문

서버가 `data` 이벤트 하나를 메시지 하나라고 해석하면 어떤 입력에서 메시지가 잘리거나 합쳐질까요? 애플리케이션이 메시지 경계를 복원하려면 어떤 규칙이 필요할까요?

## 5. 실습 03: 4바이트 길이 헤더로 프레임 복원하기

### 실행

```bash
# 터미널 1
npm run lesson:03:server

# 터미널 2
npm run lesson:03:client
```

### 예상 관찰

클라이언트는 각 payload 앞에 4바이트 big-endian 길이 헤더를 붙입니다. 첫 프레임의 헤더 일부만 먼저 쓰고, 나머지와 두 번째 프레임을 이어서 씁니다. 서버의 누적 버퍼는 시간순으로 다음과 같이 동작합니다.

1. 4바이트 헤더가 모이지 않았으면 다음 chunk를 기다립니다.
2. 헤더에서 payload 길이를 읽습니다.
3. `4 + payload 길이`만큼 모이지 않았으면 계속 기다립니다.
4. 완성된 프레임을 꺼내고 남은 바이트로 다음 프레임 복원을 반복합니다.

`data` 로그의 `decoded` 개수는 한 chunk에서 복원된 프레임 수입니다. 네트워크가 만든 chunk 경계와 무관하게 두 메시지가 원래 순서대로 복원되는 점을 확인합니다.

### 생각해 볼 질문

길이 헤더가 없으면 두 메시지의 경계를 어떻게 찾을 수 있을까요? 헤더가 비정상적으로 큰 길이를 선언할 때 서버가 제한 없이 기다리거나 메모리를 할당하면 어떤 문제가 생길까요?

## 6. 실습 04: 두 이름으로 CLI 채팅하기

### 실행

서버 하나와 클라이언트 둘이 필요하므로 터미널 세 개를 사용합니다.

```bash
# 터미널 1
npm run lesson:04:server

# 터미널 2
npm run lesson:04:client -- 민수

# 터미널 3
npm run lesson:04:client -- 지영
```

민수와 지영 터미널에서 문장을 입력하고 Enter를 누릅니다. 클라이언트는 접속 직후 이름이 든 `join` 프레임을 보내고, 이후 각 입력 줄을 `chat` 프레임으로 보냅니다. 클라이언트는 `Ctrl+C`, 서버도 실습이 끝나면 `Ctrl+C`로 종료합니다.

### 예상 관찰

두 클라이언트에 참여 시스템 메시지와 `이름: 내용` 형식의 채팅이 표시됩니다. JSON 메시지도 실습 03의 길이 헤더 프레임에 담기므로, 하나의 TCP chunk에 프레임이 붙거나 프레임 하나가 여러 chunk에 걸쳐도 디코더가 경계를 복원합니다.

서버는 앞뒤 공백을 제거한 UTF-8 바이트 수를 기준으로 이름은 최대 256바이트, 채팅 내용은 최대 8,192바이트까지 허용합니다. 상한을 넘긴 입력은 `INVALID_MESSAGE` 오류로 거부하고 해당 연결을 종료합니다. 전체 프레임 payload 상한은 실습 03과 동일하게 65,536바이트입니다.

### 생각해 볼 질문

길이 헤더는 TCP의 기능일까요, 애플리케이션 프로토콜의 기능일까요? 참여 전에 채팅을 보내거나 잘못된 JSON을 보내면 서버가 어떤 오류 프레임을 돌려줘야 할까요?

## 7. 실습 05: backpressure와 `drain`

### 실행

```bash
# 터미널 1: 읽기를 1초 멈추는 느린 소비자
npm run lesson:05:consumer

# 터미널 2: 많은 데이터를 쓰는 생산자
npm run lesson:05:producer
```

### 예상 관찰

생산자의 `socket.write()`가 `false`를 반환하면 **전송 실패가 아닙니다**. Node.js의 쓰기 버퍼가 설정된 high water mark에 도달해 더 쓰지 말고 기다리라는 흐름 제어 신호입니다. 생산자는 쓰기를 멈추고 `drain` 이벤트를 기다린 뒤 재개합니다. 소비자가 읽기를 재개하면 누적 수신 바이트가 증가합니다. `false`가 나타나는 정확한 시점과 `drain`까지 걸리는 시간, 수신 chunk 크기는 환경과 실행마다 달라질 수 있습니다.

운영 환경의 채팅 서버에는 연결마다 크기가 제한된 전송 큐를 두거나, 정해진 한계를 넘긴 느린 클라이언트의 연결을 종료하는 정책이 필요합니다. 실습 04는 backpressure를 로그로만 관찰하며, 이런 운영용 느린 클라이언트 정책의 구현은 이 프로젝트의 범위에 포함하지 않습니다.

### 생각해 볼 질문

`false`를 무시하고 계속 쓰면 애플리케이션 메모리 사용량은 어떻게 될까요? 느린 소비자가 여러 명일 때 모든 연결의 backpressure를 독립적으로 다뤄야 하는 이유는 무엇일까요?

## 8. 실습 06: FIN, half-close와 연결 종료 이벤트

### 실행

먼저 정상 종료를 실행하고, 서버를 유지한 채 강제 로컬 정리도 비교합니다.

```bash
# 터미널 1
npm run lesson:06:server

# 터미널 2
npm run lesson:06:client -- --mode=graceful
npm run lesson:06:client -- --mode=forced
```

### 예상 관찰

정상 종료에서 클라이언트의 `socket.end("client-final")`는 마지막 데이터를 쓴 뒤 자신의 송신 방향을 끝내도록 요청합니다. 로컬 쓰기가 완료되면 `finish`가 발생하고, 서버는 상대의 FIN을 받아 `end`를 관찰합니다. 서버는 `allowHalfOpen: true`이므로 상대의 송신이 끝난 뒤에도 자신의 송신 방향은 열려 있는 half-close 상태에서 `server-after-fin`을 보낸 다음 `end()`로 서버 쪽 송신을 끝낼 수 있습니다. 양방향 종료와 로컬 자원 정리가 완료되면 각 소켓에서 `close`가 발생합니다.

`--mode=forced`의 `destroy()`는 기다리던 소켓 작업을 중단하고 로컬 애플리케이션 자원을 강제로 정리하기 위한 호출입니다. 이 실습의 애플리케이션 로그만으로 특정 TCP RST 전송이나 고정된 패킷 모양을 보장하지 않습니다. OS 상태와 실행 시점에 따라 실제 패킷 관찰은 달라질 수 있습니다.

### 생각해 볼 질문

`end`, `finish`, `close`는 각각 상대의 상태, 로컬 쓰기 완료, 자원 정리 중 무엇을 알려줄까요? 한쪽이 FIN을 보낸 뒤에도 반대 방향 데이터가 흐를 수 있는 이유는 무엇일까요?

## 9. TCP의 보장과 한 번의 실행에서 관찰한 현상 구분하기

**TCP가 보장하는 것**은 한 연결 안에서 성공적으로 전달되는 바이트의 순서를 보존하는 ordered byte stream이라는 점입니다. 반면 **TCP가 보장하지 않는 것**은 애플리케이션 메시지 경계입니다. `write()` 한 번과 `data` 이벤트 한 번은 일대일 계약이 아닙니다.

따라서 다음은 한 번의 실행에서만 관찰한 비결정적 현상이며 코드가 의존해서는 안 됩니다.

- `data` 이벤트의 개수와 각 chunk 크기
- 여러 write가 합쳐지거나 한 write가 나뉘는 구체적인 방식
- 이벤트와 `drain`이 발생하는 정확한 시점
- `destroy()` 뒤 네트워크에서 보이는 구체적인 패킷 모양

애플리케이션은 길이 헤더 같은 프로토콜로 메시지 경계를 직접 만들고, backpressure와 불완전한 입력을 처리해야 합니다.

## 11. 선택 실습: Wireshark로 loopback 패킷 보기

macOS에서 Wireshark 캡처 인터페이스로 loopback인 `lo0`를 선택하고 실습 06 서버와 클라이언트를 실행합니다. 표시 필터에는 다음을 입력합니다.

```text
tcp.port == 4006
```

캡처를 시작한 뒤 클라이언트를 연결하면 먼저 `SYN` → `SYN-ACK` → `ACK`로 연결이 수립되는 과정을 확인할 수 있습니다. 그 뒤 정상 종료를 실행해 양쪽의 `FIN` 교환을 관찰하고, 강제 로컬 정리 실행과 비교합니다. 재전송 여부, 세그먼트가 보이는 개수와 묶임, `FIN` 전후의 구체적인 `ACK` 표현은 Node.js API 호출만으로 미리 단정하지 않습니다. 패킷 캡처는 현재 OS와 실행 타이밍에서 나온 관찰 증거로 다룹니다.
